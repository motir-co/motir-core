Repositories — what each repository starts from

MOTIR-705 · story MOTIR-704. A DELTA on design/repository-set/repositories-room.mock.html, drawing only what changes: a repository Motir creates now starts from a starter chosen out of Motir’s starter library, and the row says which one, where the repository is hosted, and — while it is not created yet — why that starter was chosen and how to pick another.

The seed lives in the room, not on the plan approval step. Since MOTIR-5014 the approval step lists no repositories and asks nothing about them (design/repository-set/design-notes.md §0, §4); the room already lists every repository Motir creates, including the ones not created yet, in its Hosted by Motir section. The approval step is not redrawn.

Panel 1 · Project settings → Repositories — two repositories not created yet, each with its starter, its hosting and why it was chosen; the organisation’s repository is unchanged

A Motir-created row gains two pills after its state: the starter (lavender) and the hosting target (sky). A row that is not created yet also shows Why this starter and the Starter picker. The row from the organisation shows neither pill — Motir never seeds a repository it did not create.

Panel 2 · Matched — a web repository on each of the three hosting targets, and a soft criterion the starter does not serve

Hosting and role are hard: a starter that does not deploy where the repository runs is never chosen. Use and size are soft. When the best starter for the target does not serve the repository’s use or size, the fact says so (not served) instead of hiding it. Only the rows are drawn; each sits in the Hosted by Motir section of Panel 1.

Panel 3 · The defaults, shown as defaults — no stack named, no hosting target yet, no starter matched, and a mobile repository with no hosting

Each of the four non-matches says what was missing and what the repository falls back to. A default is never dressed up as a match: the facts show Not named or Not set where the plan gave nothing, and the starter pill carries a Default pill beside it.

Panel 4 · The Starter picker, open — only the starters this repository can start from

The picker lists only active starters of the row’s role that deploy to the row’s hosting target, then Initialised repository, which fits every repository. A retired starter, another role’s starter or another target’s starter is never offered. On the left, a web repository on Serverless; on the right, a web repository with no hosting target yet, which every web starter fits. The footer says what the list is filtered by.

Panel 5 · Refused changes — the starter is saved by the server, which can still say no

The picker offers only starters that fit, so a refusal means the library changed after the list loaded, or the row did. The alert sits under the picker, the picker keeps the saved starter, and the list reloads. Each refusal names its rule: a different hosting target, a retired starter, another role’s starter, and a repository that already exists. The copy is the route’s typed refusal (refusal) put in the person’s words.

Panel 6 · Created — the starter and hosting stay on the row, read-only

Once a repository is created its starter is history: the row keeps both pills, drops Why this starter and the picker, and its detail line names the starter it actually started from instead of the fixed “seeded from the Motir Next.js starter”. The Move to my GitHub action and the rest of the row are unchanged.
